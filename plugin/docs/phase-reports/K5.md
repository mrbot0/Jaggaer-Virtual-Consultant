## Scostamenti e decisioni

1. **Ordine dei commit**: K5.6 prima di K5.5, perché la verifica 3A di guard-production usa la
   funzione condivisa di `approvals.mjs` (`threeAState`).
2. **`session.env` è una copia validata** della voce di environments.yaml (e di
   remediation-scope.yaml) con i loro sha256: i guard non analizzano YAML né caricano Ajv, e negano
   se i file cambiano dopo `use env` («riesegui /use env»).
3. **`second_approver_required`** vale `true` per default in prod (se il file tace), `false`
   altrove; `prod_allowed_red` `[]`, `config_window_minutes` 60.
4. **Giallo in sandbox/preprod = A1 + A3 del passo** (§57.2), quindi il token per passo serve anche
   per il giallo, non solo per rosso e prod; rosso = A1 + A2 + A3; verde = A1; prod = sempre 3A.
5. **Record `consume`** nel registro (oltre ad A1/A2/A3/action): il monouso è un fatto della catena.
6. **Hook paralleli**: guard-production accetta un token A3 consumato da al più 30 s (lo consuma
   guard-config-scope nella stessa chiamata); il monouso lo garantisce guard-config-scope.
7. **guard-config-scope**, dettagli: compensazione richiesta per ACT-CREATE/UPDATE/SUBMIT quando il
   verbo salva (SAVE/SUBMIT/TOGGLE/UPLOAD); snapshot ≤ 60 s richiesto a ogni azione con effetto di un
   passo ACT-CFG-CHANGE; ACT-UPLOAD fra le classi sorvegliate; azioni R2 sui dati = il `sì` del passo
   (record `action`, consumato); ACT-BULK = A1 + A3; script o strumenti non classificati durante un
   passo sorvegliato ⇒ deny; in modalità `config` senza piano attivo ogni azione con effetto ⇒ deny.
8. **Il piano approvato è fissato**: A1 registra lo sha256 del file del piano; un piano cambiato dopo
   A1 ⇒ deny.
9. **Anche i tentativi respinti vanno in audit** (senza il testo del prompt, solo lo sha256).
10. **Le richieste in `pending.approvals` e `active_plan`** le scrive step-check (K6); la CLI
    `approvals.mjs` resta in sola lettura come da brief. Un piano è approvabile se è nelle richieste
    aperte o è il piano attivo.
11. **Schema del piano**: `approvals: "3A"` a livello di piano e `config { object, area, level }` a
    livello di passo; validate-plan richiede `action_class` su ogni passo e `config` sui passi di
    configurazione con effetto.
12. **Atlas**: voci SEL in `kb/scopes/<SCOPE>/selectors/<codice>.yaml` (layout §8.2) con i campi
    `role` e `effect`; S da `product/kb`, C/L solo del cliente attivo.
13. **Matcher del browser più largo delle tre famiglie**: ogni server MCP con chrome/browser/
    playwright/puppeteer/selenium/devtools nel nome; ciò che non si classifica è `other` ⇒ deny.
14. **Script fuori prod**: consentiti senza primitive di rete/navigazione, o se ogni URL letterale è di
    un host dichiarato (almeno uno); codice dinamico (eval, accessi calcolati, atob, escape) ⇒ deny.

## Rischi residui

- **Lo snapshot di env-check lo salva l'agente**: la verifica dell'impronta vale quanto lo snapshot.
  Restano comunque l'allow-list degli host e il divieto di scrittura in prod.
- **Il guard non lega l'uid/ref MCP al SEL del passo**: può verificare il passo e la voce
  dell'Atlas, non che l'elemento cliccato sia quello. Mitigazioni: piano codificato, step-check (K6),
  persone solo amministrative in prod (strato 4 di §52.1).
- **`browser.current_url` lo mantiene observe-append (K6)**: fino ad allora, dopo un redirect del
  browser verso un host non dichiarato, le azioni successive sono bloccate solo se la navigazione
  stessa era verso l'host non dichiarato.
- **Scritture offuscate su approvals.jsonl o sul transcript** (per esempio `node -e` che costruisce il
  nome del file a runtime) sfuggono all'analisi dei comandi. Per questo un token vale solo se la frase
  compare anche come messaggio dell'utente nel transcript: un attaccante dovrebbe falsificare entrambi.
- **Il nome del secondo approvatore è dichiarato, non autenticato**: il controllo è organizzativo
  (§52.2 lo dice).
- **Un `sì`** è confermato nel transcript da qualunque messaggio `sì`: vale solo con una sola
  richiesta di azione aperta, e solo per quel passo.
- **Token monouso alla prima azione con effetto del passo**: un passo che richiede due azioni con
  effetto va diviso in due passi del piano.
- La semantica dei matcher di Claude Code non è verificata: ogni guard ricontrolla `tool_name`.

Rischi residui, detti in modo onesto:

- **Canali che consegnano un vero prompt dell'utente.** Il `sendPrompt` di un widget e il
  `send_message` di una sessione verso se stessa arrivano ad approval-capture come prompt
  dell'utente. Se la frase di approvazione è offuscata nell'input dello strumento (concatenazioni,
  entità HTML, caratteri a larghezza piena), guard-phrase non la vede. Il prompt risultante è
  autentico per approval-capture e per il transcript, quindi **i controlli a valle non la
  intercettano**. Con un ambiente dichiarato, l'allow-list dei server MCP (I5) nega questi strumenti.
  Senza ambiente dichiarato, il canale resta aperto: lo chiude solo il divieto di questi strumenti o
  un controllo organizzativo.
- Protezione delle impostazioni e del plugin via shell. Si nega ogni **menzione testuale**. Un nome
  costruito a runtime (`'.cla'+'ude'`, variabili, codifiche) oppure un modulo importato da uno script
  eseguito sfugge. 3A e i guard resistono agli errori e alla prompt injection, non a un modello
  determinato che gira come lo stesso utente del sistema operativo.
- Scrivere nella cartella padre del plugin con operazioni ad albero (`cp x ~`) è negato: ne risulta
  qualche attrito, sempre nel verso sicuro.
- L'URL effettivo è quello che il server del browser riporta. Un click su un link, `ctrl+Tab` o un
  click con modificatori cambiano pagina senza una risposta di navigazione. observe-append (K6)
  resta un **prerequisito bloccante** prima che un agente usi il browser.
